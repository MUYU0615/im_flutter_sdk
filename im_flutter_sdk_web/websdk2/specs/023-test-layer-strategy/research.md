# 研究结论：工程测试分层方案（Phase 0）

> 目的：消除三层测试落地过程中的关键不确定性，形成可执行决策。

## 决策 1：PR 门禁采用“三层中的前两层”

- **Decision**: PR 阶段阻断单元测试 + mock 协议集成测试；E2E 不进入每次 PR 必跑集合，真实环境验证迁为独立 smoke。
- **Rationale**: 该组合在“问题发现时效”与“执行时长”之间最平衡，且不受后端环境波动影响，满足 10 分钟级门禁目标。
- **Alternatives considered**:
  - 全部三层都阻断 PR：覆盖高但耗时波动大，影响研发节奏。
  - PR 中加入真实环境：后端波动会放大前端门禁噪音。

## 决策 2：E2E 采用“定时执行 + 发布前强制通过”

- **Decision**: E2E 由定时任务执行，且主干发布前最近一次执行结果必须通过。
- **Rationale**: 浏览器场景价值高但波动性和耗时高，适合作为发布前质量闸门而非每次 PR 闸门。
- **Alternatives considered**:
  - PR 全量执行 E2E：反馈慢，影响合并效率。
  - 仅定时执行不设发布门禁：发布前缺少最终浏览器侧质量保障。

## 决策 3：真实环境不可达执行自动重试，但不纳入 gate

- **Decision**: 真实环境 smoke 入口保留自动重试与失败证据，但不再阻断 PR / Nightly / Release gate。
- **Rationale**: 可保留真实接入可用性信息，同时避免“环境不可达”污染前端集成测试结论。
- **Alternatives considered**:
  - 首次失败立即阻断：误报率高。
  - 完全删除真实环境验证：会放大 mock 与线上漂移风险。

## 决策 4：真实环境只保留为独立 smoke 核心主链路

- **Decision**: 真实环境 smoke 仅覆盖连接、鉴权、发消息、收消息、回执等核心主链路。
- **Rationale**: 真实环境用于协议一致性与可用性对齐，但不适合承担日常集成回归。
- **Alternatives considered**:
  - 在真实环境覆盖所有异常：成本高且可重复性差。
  - 仅做连通性探活：覆盖不足，无法发现主链路语义回归。

## 决策 5：异常链路以 mock server 为主

- **Decision**: 超时、断连、乱序、重复响应、非法响应等异常场景由 mock server 稳定注入并回归。
- **Rationale**: mock 注入可控、可复现、可并行，最适合高频异常回归。
- **Alternatives considered**:
  - 依赖真实服务制造异常：复现不稳定且调试成本高。
  - 仅用单元 mock：无法覆盖协议层与传输层交互行为。

## 决策 6：E2E 载体使用无头浏览器驱动真实 demo 页面

- **Decision**: E2E 使用无头浏览器驱动现有 demo 主页面，并通过真实环境凭证验证初始化、登录连接、发送消息与登出等高价值主链路。
- **Rationale**: 可验证 localStorage、页面刷新、网络切换等 Node 测试无法完整覆盖的行为。
- **Alternatives considered**:
  - 仅 Node 集成：无法覆盖浏览器特有行为。
  - 仅人工点测 demo：不可稳定回归，缺少自动化门禁价值。

## 决策 7：测试数据采用“账号池 + 场景前缀 + 用后清理”

- **Decision**: 每个场景使用独立数据前缀与可复用账号池，执行后进行最小清理，避免会话污染。
- **Rationale**: 减少并发冲突与脏数据导致的假失败，提升定时任务稳定性。
- **Alternatives considered**:
  - 全局共享固定账号与会话：冲突概率高。
  - 每次全新申请账号：成本高且难自动化。

## 决策 8：失败证据统一结构化输出

- **Decision**: 每次失败至少输出测试层级、场景 ID、失败原因、时间戳、重试次数（如有）。
- **Rationale**: 保障 SC-004 可追溯性目标，减少排障往返。
- **Alternatives considered**:
  - 仅保留框架默认日志：信息碎片化，不利于归因。
  - 失败时导出完整调试包：成本高，不适合作为最小标准。
