# Feature Specification: 工程测试分层规范

**Feature Branch**: `023-test-layer-strategy`  
**Created**: 2026-03-06  
**Status**: Draft  
**Input**: User description: "当前工程里的测试主要依赖单元测试，但是缺少真实环境测试；保留现有单元测试，新增协议/集成测试（支持 mock server 异常场景）和 E2E 测试，线上测试暂不纳入。"

## Clarifications

### Session 2026-03-06

- Q: 真实环境与 E2E 的门禁级别怎么定？ → A: PR / Nightly / Release gate 只跑单元 + mock 集成 + E2E；真实环境保留为独立 smoke。
- Q: 当真实测试环境不可达时，PR 门禁如何判定？ → A: 不再影响 PR gate，由独立 smoke 入口保留重试与失败证据。
- Q: 协议/集成层里“真实环境用例”和“mock 异常用例”的覆盖边界怎么定？ → A: 集成层只保留 mock/local-only 场景；真实环境只作为独立 smoke 覆盖核心主链路。

## User Scenarios & Testing _(mandatory)_

### User Story 1 - 协议链路真实可用验证 (Priority: P1)

作为 SDK 维护者，我希望在真实测试环境中验证连接、鉴权、消息收发等核心协议链路，确保发布前能发现与真实服务交互相关的问题。

**Why this priority**: 该能力直接弥补“只有单元测试、缺少真实环境验证”的主要风险，优先级最高。

**Independent Test**: 独立执行协议/集成测试套件，在真实测试环境中完成核心链路验证并产出通过/失败结果。

**Acceptance Scenarios**:

1. **Given** 测试环境可访问且测试账号可用，**When** 执行协议/集成测试，**Then** 连接、鉴权、消息发送、消息接收、确认回执链路全部可验证并输出结果。
2. **Given** 测试环境返回业务错误码，**When** 执行协议/集成测试，**Then** SDK 对外行为符合预期错误映射与状态变化定义。

---

### User Story 2 - 异常场景稳定复现与回归 (Priority: P1)

作为 SDK 维护者，我希望通过 mock server 可控注入异常，稳定复现真实服务难以触发的故障场景，保证异常处理逻辑可回归验证。

**Why this priority**: 异常处理是实时通信稳定性的核心风险点，且难以仅依赖真实环境稳定覆盖。

**Independent Test**: 独立执行 mock server 异常用例集，验证超时、断连、乱序、无效响应等场景下 SDK 的预期行为。

**Acceptance Scenarios**:

1. **Given** mock server 注入超时与断连异常，**When** 执行协议/集成异常测试，**Then** SDK 能触发预期重试或失败流程并输出明确错误结果。
2. **Given** mock server 注入乱序或不完整响应，**When** 执行协议/集成异常测试，**Then** SDK 能按既定容错策略处理且不产生未定义状态。

---

### User Story 3 - 浏览器端真实 demo 主链路验证 (Priority: P2)

作为 SDK 使用方，我希望在无头浏览器中自动运行真实 demo 页面并连接真实测试环境，验证 SDK 在浏览器中的初始化、登录、连接、发送消息与登出主链路，避免 E2E 只验证本地假状态机而无法发现真实接入回归。

**Why this priority**: 对 IM SDK 而言，浏览器侧真实接入链路比 demo 页面本地状态切换更有价值；需要通过真实 demo + 真实环境来验证最终交付形态。

**Independent Test**: 独立执行无头浏览器 E2E 套件，完成真实 demo 页面中的初始化、登录连接、文本消息发送、登出等关键路径验证。

**Acceptance Scenarios**:

1. **Given** 真实 demo 页面可启动且测试账号可用，**When** 执行无头浏览器 E2E，**Then** SDK 初始化、登录并建立连接链路可端到端通过。
2. **Given** 真实 demo 页面已连接且存在有效目标会话，**When** 执行文本消息发送用例，**Then** 浏览器页面可观察到发送成功结果，且消息状态进入 `sent`。
3. **Given** demo 页面初始化时填写了无效 `AppKey`，**When** 用户尝试登录，**Then** 页面必须明确失败并保持未连接状态，不能出现“假通过”。
4. **Given** demo 页面已成功登录连接，**When** 用户执行登出，**Then** 页面状态恢复为未连接，当前用户信息被清空。

### Edge Cases

- 真实测试环境短时不可达时，如何区分“环境故障”与“SDK 回归”并给出可判读结果。
- mock server 同时注入多类异常（例如断连 + 延迟 + 重复响应）时，系统是否仍能保持确定性结果。
- 浏览器标签页刷新、会话切换、缓存残留导致状态污染时，E2E 是否能保证用例隔离与稳定执行。
- demo 页面从环境变量预填参数时，E2E 是否仍通过页面显式填值避免“改了环境却没生效”的误判。
- 测试账号配额耗尽或并发占用时，测试是否能快速失败并输出可定位原因。

## Requirements _(mandatory)_

### Functional Requirements

- **FR-001**: 系统 MUST 保留并持续执行现有单元测试层，作为基础质量门禁。
- **FR-002**: 系统 MUST 提供协议/集成测试层，并使用 mock server 或本地可控依赖覆盖 SDK 的连接、鉴权、消息收发与回执核心路径。
- **FR-003**: 系统 MUST 在协议/集成测试层提供 mock server 场景能力，用于可控注入异常行为。
- **FR-004**: 系统 MUST 为每个异常场景定义可验证的期望结果，至少包含错误结果、状态变化或恢复行为之一。
- **FR-005**: 系统 MUST 提供浏览器 E2E 测试层，通过无头浏览器验证真实 demo 页面接入真实测试环境后的关键用户流程。
- **FR-006**: 系统 MUST 支持测试数据隔离机制，避免不同用例间账号、会话或消息数据互相污染。
- **FR-007**: 系统 MUST 提供分层执行策略，并明确快速门禁为“单元 + mock 集成”，不依赖真实后端环境。
- **FR-008**: 系统 MUST 明确 E2E 采用定时执行，且在主干发布前作为必过门禁。
- **FR-009**: 系统 MUST 在测试失败时输出可定位信息，至少包含测试层级、场景标识与失败原因。
- **FR-010**: 系统 MUST 明确本特性范围不包含线上合成监控与生产环境主动探测。
- **FR-011**: 系统 MUST 提供统一的工程文档，说明三层测试的目标、适用场景与执行入口。
- **FR-012**: 系统 MUST 保留独立真实环境 smoke 入口，在真实环境不可达时执行自动重试并输出失败证据。
- **FR-013**: 系统 MUST 将真实环境验证范围限定为 smoke 核心主链路，不纳入协议/集成 gate。
- **FR-014**: 系统 MUST 将异常链路覆盖主要放在 mock server 场景中执行与回归。
- **FR-015**: 系统 MUST 在 E2E 层覆盖真实 demo 页面中的初始化与登录连接主链路，并校验浏览器页面状态与当前用户信息。
- **FR-016**: 系统 MUST 在 E2E 层覆盖真实 demo 页面中的文本消息发送成功场景，并验证页面日志或消息列表可观测到成功结果。
- **FR-017**: 系统 MUST 在 E2E 层覆盖无效 `AppKey` 等关键配置错误场景，确保浏览器侧不会出现“假通过”。
- **FR-018**: 系统 MUST 在 E2E 层覆盖真实 demo 页面中的登出主链路，并验证状态恢复与用户上下文清理。

### Key Entities _(include if feature involves data)_

- **TestLayerDefinition**: 测试层定义，描述单元测试、协议/集成测试、E2E 测试的职责边界与准入要求。
- **ScenarioCatalog**: 场景目录，维护核心路径场景与异常场景的唯一标识、前置条件与预期结果。
- **EnvironmentProfile**: 环境画像，定义真实测试环境与 mock 环境的连接信息、可用性要求与限制条件。
- **TestDataScope**: 测试数据作用域，描述账号、会话、消息数据的隔离策略与清理策略。
- **ExecutionPolicy**: 执行策略，定义快速门禁与全量执行的触发条件、覆盖范围与结果判定标准。
- **FailureEvidence**: 失败证据，记录测试层级、场景标识、失败时间与失败摘要，支持回归分析。

### Assumptions

- 公司已提供可用于自动化验证的真实测试环境与测试账号。
- 工程内已有可用于浏览器端验证的真实 demo 页面入口。
- 线上环境的合成监控由专门测试工程负责，本特性仅覆盖本地与 CI 可执行的三层测试。

## Success Criteria _(mandatory)_

### Measurable Outcomes

- **SC-001**: 核心协议链路（连接、鉴权、发消息、收消息、回执）在真实测试环境均具备自动化验证用例，覆盖率达到 100%。
- **SC-002**: 约定的高风险异常场景（超时、断连、乱序、无效响应）均具备可重复执行的 mock 验证用例，覆盖率达到 100%。
- **SC-003**: 每次变更的快速门禁（单元 + mock 集成）执行完成时长不超过 10 分钟，且可稳定给出通过/失败结论。
- **SC-004**: 全量测试执行中，三层测试结果均可追溯到具体场景标识，失败定位信息完整率达到 100%。
- **SC-005**: 浏览器 E2E 的真实 demo 主链路（初始化、登录、发送、登出）首轮通过率在稳定环境下达到 95% 及以上。
- **SC-006**: 主干发布前最近一次 E2E 执行结果必须为通过，达成率 100%。
- **SC-007**: 真实环境不可达场景下，独立 smoke 入口可在重试后稳定输出“环境不可达”的明确结论，结论可读率达到 100%。
- **SC-008**: 真实环境 smoke 用例集中，核心主链路覆盖率达到 100%，且不引入非核心异常链路的强制覆盖要求。
- **SC-009**: mock 异常用例集中，约定高风险异常场景覆盖率达到 100%。
- **SC-010**: 真实 demo E2E 关键场景覆盖清单（初始化、登录连接、无效 `AppKey` 失败、文本消息发送、登出恢复）达成率 100%。
