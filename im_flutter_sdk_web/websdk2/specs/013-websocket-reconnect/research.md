# 研究结论：实时连接重连逻辑

> 目的：消除技术上下文中的不确定性，形成可执行的实现决策。

## 决策 1：统一重连入口与防并发锁

- **Decision**: 所有重连触发点统一进入一个重连方法，方法内检查“已连接/重连中”状态并直接返回。
- **Rationale**: 避免多触发点并发重连导致连接状态破坏、事件重复与资源浪费。
- **Alternatives considered**: 各触发点独立实现重连逻辑（实现快但易产生竞态与重复连接）。

## 决策 2：区分登录阶段与登录后阶段的重连上限处理

- **Decision**: 登录阶段达到最大重连次数时由 `login()` 抛出失败并停止自动重连；登录后场景达到上限时进入 onReconnectFailed，但在收到 online 事件后继续重连。
- **Rationale**: 登录阶段失败需要明确的同步失败反馈；登录后场景以自动恢复为目标，online 事件是可靠的恢复信号。
- **Alternatives considered**: 统一在达到上限后永久停止重连（会导致登录后无法自动恢复）。

## 决策 3：offline 主动关闭连接，online 作为恢复入口

- **Decision**: 监听 offline 事件后主动关闭 WebSocket，并暂停所有重连；online 事件触发重连（仅在已登录状态且允许重连时）。
- **Rationale**: 避免 online 事件到来时 WebSocket 仍处于“连接中/已连接”的假状态，导致无法重连；离线期间避免无意义的重连循环。
- **Alternatives considered**: 仅依赖 WebSocket close/error（离线时可能无 close 回调）。

## 决策 4：前台恢复触发心跳健康检查

- **Decision**: 已登录状态下页面回到前台时发送心跳/探测消息，失败或超时即触发重连。
- **Rationale**: 后台长时间可能断开但无断线事件，前台需要快速自检。
- **Alternatives considered**: 前台恢复即直接重连（可能打断已稳定连接）。

## 决策 5：发送超时触发重连

- **Decision**: 任何发送操作超过超时阈值时触发重连。
- **Rationale**: 发送超时通常意味着连接不可用，重连是最快的恢复方式。
- **Alternatives considered**: 只重试发送不重连（可能在坏连接上继续失败）。

## 决策 6：连接成功后重置计数与状态

- **Decision**: 连接成功后清零重连计数与失败状态。
- **Rationale**: 避免成功后仍被“已达上限”状态阻断后续重连。
- **Alternatives considered**: 保留历史计数用于统计（可另行记录但不影响逻辑）。
