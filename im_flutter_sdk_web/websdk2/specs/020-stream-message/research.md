# 020 研究记录（Phase 0）

## Decision 1: 本期仅实现流式消息接收与回调，不支持发送

- **Decision**: SDK 仅在接收链路处理流式分片并回调；发送入口遇到流式消息时返回明确“不支持”错误。
- **Rationale**: 用户需求明确排除发送能力，可降低实现面并减少对既有发送链路的回归风险。
- **Alternatives considered**:
  - 同期支持发送：范围扩大，超出本期目标。
  - 隐式忽略发送请求：会造成业务误判为成功或无反馈。

## Decision 2: 每次回调同时提供累计全文与本片增量文本

- **Decision**: 流式事件中同时暴露 `fullText`（当前累计）与 `deltaText`（本片增量）。
- **Rationale**: 同时满足实时逐片渲染与直接显示完整内容两类场景，减少业务侧二次拼接成本。
- **Alternatives considered**:
  - 仅 delta：业务需自行累加，易出错。
  - 仅 full：难以支持逐字动画等增量体验。

## Decision 3: 缺片处理采用“等待补齐 + 兜底末片完成”

- **Decision**: 中间缺片时先缓存等待；若后续收到带完整文本的兜底末片，则允许直接完成该流。
- **Rationale**: 对齐旧工程语义，兼顾严格顺序与弱网可用性。
- **Alternatives considered**:
  - 缺片即失败：在抖动网络下失败率过高。
  - 永远等待补齐：可能导致流长期悬挂。

## Decision 4: 超时判定仅信任服务端错误分片

- **Decision**: SDK 不引入本地超时计时器；仅在收到服务端超时错误分片时回调一次错误态并结束流。
- **Rationale**: 可避免本地与服务端双计时冲突，保证错误语义一致；用户已明确单片超时会收到错误码 512。
- **Alternatives considered**:
  - 本地计时兜底：可能与服务端判定重复触发结束。
  - 本地计时主导：与现网协议语义不一致。

## Decision 5: 并行顺序语义为“单流严格有序，跨流按到达顺序”

- **Decision**: 单条流内按 seq 连续回调；多流并行不做全局串行，按到达顺序分发。
- **Rationale**: 在保证单流正确性的前提下降低调度复杂度，提升整体实时性。
- **Alternatives considered**:
  - 全局严格有序：实现复杂，且会放大慢流对快流的阻塞。
  - 跨流顺序完全不保证：可观测性与调试体验变差。

## Decision 6: 缓存会话唯一键采用 msgId

- **Decision**: 仅使用 `msgId` 聚合分片、去重与清理。
- **Rationale**: 与用户澄清一致，且协议假设在接收窗口内 `msgId` 唯一。
- **Alternatives considered**:
  - `msgId + 会话维度` 组合键：更保守，但与已确认约束不一致。
  - 优先 streamId 回退 msgId：引入额外分支与兼容复杂度。

## Decision 7: 完成后清理与重复保护

- **Decision**: 流完成（正常/兜底/错误）后立即释放缓存，并丢弃后续重复或过期分片。
- **Rationale**: 防止重复回调与内存占用增长，保证每条流单次完成。
- **Alternatives considered**:
  - 延迟清理：增加重复触发窗口。
  - 永久保留近期会话：收益低且增加内存成本。
