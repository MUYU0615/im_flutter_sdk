## Clarifications

### Session 2026-02-25

- Q: 流式回调中的文本语义应如何定义？ → A: 同时回调累计全文与本片增量文本。
- Q: 缺片等待超时后的对外行为应如何定义？ → A: 回调一次错误态分片并结束该流；单片超时场景服务端会下发错误码 512。
- Q: 超时判定来源应如何定义？ → A: 仅以服务端下发的超时错误分片为准，SDK 不做本地超时计时。
- Q: 多条流并行时的回调顺序约束应如何定义？ → A: 仅保证单流内有序，跨流按到达顺序回调。
- Q: 流缓存会话的唯一键应如何定义？ → A: 仅使用消息 ID 作为缓存键。

## 用户场景与测试 _(mandatory)_

### 用户故事 1 - 按顺序回调流式分片（Priority: P1）

作为 SDK 使用者，我希望在接收到流式消息时，SDK 能按正确顺序逐片回调，避免业务层自行做乱序处理。

**Why this priority**: 顺序回调是流式展示体验的核心，直接影响最终文本内容和用户可读性。

**Independent Test**: 仅实现该故事即可通过“乱序到达 + 缺片补齐”的输入验证顺序回调能力。

**Acceptance Scenarios**:

1. **Given** 服务端下行一条多分片流式消息，**When** 首片到达，**Then** SDK 创建该流的缓存会话并回调首片。
2. **Given** 某流存在未到达分片，**When** SDK 收到后续更大序号分片，**Then** SDK 暂存后续分片且不提前回调越序内容。
3. **Given** 缺失分片随后补齐，**When** SDK 进行顺序检查，**Then** SDK 依序回调此前缓存的可连续分片。
4. **Given** 同一流分片重复下行，**When** SDK 完成去重判断，**Then** 重复分片不产生重复回调。

---

### 用户故事 2 - 缺片场景的兜底完成（Priority: P1）

作为 SDK 使用者，我希望在中间分片缺失时，SDK 能在等待补齐失败后接受“最后一片完整文本”的兜底语义，保证最终可展示完整内容。

**Why this priority**: 网络抖动下缺片不可避免，兜底机制决定流式消息最终可用性。

**Independent Test**: 仅实现该故事即可通过“缺片不补齐 + 兜底末片到达”验证最终完成路径。

**Acceptance Scenarios**:

1. **Given** 流式消息存在中间缺片，**When** 缺失分片未及时到达，**Then** SDK 继续等待并保留当前缓存状态。
2. **Given** 该流最终收到携带完整文本的兜底末片，**When** SDK 识别该兜底语义，**Then** SDK 回调该末片并将该流标记为完成。
3. **Given** 缺片已补齐并完成正常收尾，**When** SDK 结束该流，**Then** 该流缓存被清理且不再接收重复完成回调。

---

### 用户故事 3 - 单片与非目标能力边界（Priority: P2）

作为 SDK 使用者，我希望明确流式能力边界：支持接收回调，不支持发送；并在单片流式场景下得到稳定语义。

**Why this priority**: 明确能力边界可减少误用，单片语义可覆盖服务端降级或短文本场景。

**Independent Test**: 仅实现该故事即可验证 `STREAM_FULL` 单片回调和“不支持发送流式消息”的错误语义。

**Acceptance Scenarios**:

1. **Given** 某条流式消息仅有一个分片，**When** SDK 接收该分片，**Then** 该分片状态为 `STREAM_FULL` 且仅回调一次。
2. **Given** 业务侧尝试通过 SDK 发送流式消息，**When** 调用发送入口，**Then** SDK 返回明确的不支持错误且不发起发送流程。
3. **Given** SDK 接收普通非流式消息，**When** 执行现有接收链路，**Then** 普通消息回调行为保持不变。

### Edge Cases

- 首片缺失但中间片先到达时，缓存启动与回调时机如何保持一致。
- 同一流并发到达多个乱序分片时，顺序回调与去重的一致性。
- 缺片长期未补齐且也未收到兜底末片时，缓存的超时清理与可观测结果。
- 单片流式超时时服务端下发错误码（如 512）后，错误回调与清理时机一致性。
- 兜底末片到达后又收到历史缺片时，是否忽略并避免二次完成。
- 多条流（同会话/不同会话）并行接收时，缓存隔离与串流污染防护。
- 单片 `STREAM_FULL` 与多片流的状态判断边界（例如错误标记为 FULL）。

## Requirements _(mandatory)_

### Functional Requirements

- **FR-001**: SDK MUST 支持接收流式消息并通过对外回调逐片输出。
- **FR-002**: SDK MUST 不提供流式消息发送能力；业务侧触发发送时必须返回明确“不支持”错误。
- **FR-003**: SDK MUST 在同一流首片到达时创建缓存会话并记录流式上下文。
- **FR-004**: SDK MUST 按分片序号执行顺序校验；存在缺片时必须缓存后续分片并等待缺失补齐。
- **FR-005**: SDK MUST 在缺失分片补齐后按序回调所有连续可交付分片，且每片仅回调一次。
- **FR-006**: SDK MUST 支持“兜底末片包含完整文本”的完成语义；在缺片未补齐时收到该末片，允许以该末片完成该流。
- **FR-007**: SDK MUST 在流完成后释放该流缓存，避免重复完成或内存长期占用。
- **FR-008**: SDK MUST 在单片流式场景输出状态 `STREAM_FULL`，并保证只产生一次回调。
- **FR-009**: SDK MUST 对同一流的重复分片进行去重，避免重复回调。
- **FR-010**: SDK MUST 在多条流并行接收时保持缓存隔离，避免不同流之间的数据串扰。
- **FR-011**: SDK MUST 保持普通非流式消息接收行为不回归。
- **FR-012**: SDK MUST 提供可识别的失败语义，覆盖缺片超时、无效分片、状态不一致等异常场景。
- **FR-013**: SDK MUST 在每次流式回调中同时提供“当前累计全文”和“当前分片增量文本”两类文本语义。
- **FR-014**: SDK MUST 在缺片超时场景回调一次错误态分片并结束该流（清理缓存）；单片超时时需正确承接服务端下发的超时错误码（如 512）语义。
- **FR-015**: SDK MUST 以服务端下发的超时错误分片作为唯一超时判定来源；不得引入本地超时计时触发流终止。
- **FR-016**: SDK MUST 保证“单条流内严格有序回调”，并在多流并行场景下允许跨流按到达顺序回调。
- **FR-017**: SDK MUST 仅使用消息 ID 作为流缓存会话的唯一键，并据此执行分片聚合、去重与清理。

### Key Entities _(include if feature involves data)_

- **StreamMessageChunk**: 流式消息分片实体，包含流标识、分片序号、分片状态与文本内容。
- **StreamAssembleSession**: 单条流的缓存会话，记录已收分片、缺失序号、完成状态与最后一次活动时间。
- **StreamMessageEvent**: SDK 对外回调事件，包含当前分片内容、分片状态、顺序信息与所属消息上下文。

### Assumptions

- 服务端协议会为同一条流式消息提供可关联的流标识与可比较的分片顺序信息。
- 同一消息 ID 在流式接收窗口内保持唯一，可作为缓存会话唯一键。
- “兜底末片”由服务端明确标识，且该分片携带可直接展示的完整文本内容。
- 服务端会在超时场景下下发可识别错误分片（例如单片超时错误码 512）用于驱动流终止。

## Success Criteria _(mandatory)_

### Measurable Outcomes

- **SC-001**: 流式分片乱序输入场景下，顺序回调正确率达到 100%。
- **SC-002**: 缺片补齐场景下，补齐后连续分片按序回调通过率达到 100%。
- **SC-003**: “缺片未补齐 + 兜底末片到达”场景下，最终完成与回调结果正确率达到 100%。
- **SC-004**: 单片 `STREAM_FULL` 场景测试通过率达到 100%，且重复回调次数为 0。
- **SC-005**: 重复分片去重场景中，重复分片误回调率为 0。
- **SC-006**: 非流式消息回归用例通过率达到 100%，确认不引入接收链路行为回归。
- **SC-007**: 超时失败场景中，错误态回调次数为 1 且流缓存清理成功率达到 100%（含单片超时错误码场景）。
