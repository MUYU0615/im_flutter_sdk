# 功能规格：联系人自动同步（阶段一）

**Feature Branch**: `024-contact-sync`  
**Created**: 2026-03-17  
**Status**: Draft  
**Input**: 用户需求："起草 024 spec，联系人模块分两部分：一部分是登录后自动同步联系人；另一部分是补充原工程里的联系人相关 API。当前阶段只先实现自动同步联系人，联系人 API 补充延后处理。"

**Reference**:

- 联系人版本元数据查询接口：`GET /{org}/{app}/user/{username}/roster/metadata/version`
- 联系人同步网关协议：`easemob.imfusion.gateway.v1.RosterService`

## Clarifications

### Session 2026-03-18

- Q: 联系人同步结果里的 `nickname/avatarUrl/sign` 真正来源是什么？ → A: `RosterItem.metadata` 中携带并解析 `nickname/avatarUrl/sign`，联系人同步时直接解析并顺手更新 `userInfo` 缓存。
- Q: 删除联系人如何在增量同步里表达？ → A: 新增联系人走增量同步；删除联系人时切到全量同步。
- Q: 如果 metadata version 查询失败，登录后的联系人同步该怎么降级？ → A: 有完整本地缓存就先用缓存并派发失败事件；没有完整缓存就继续尝试一次全量同步。
- Q: 联系人同步失败结果要不要区分失败阶段？ → A: 要区分；不再单独暴露 `onContactSyncFail`，而是在 `onContactSyncFinish.error` 中返回失败阶段信息。
- Q: 联系人同步 websocket 地址从哪里来？ → A: 从 DNS 获取，优先使用 `sync-ws` 数组；连接前可先随机打散，某个地址失败后切下一个地址。若 DNS 缺少 `sync-ws` 或补拉 DNS 失败，本轮自动联系人同步仍需派发 `onContactSyncStart` 与带 `error` 的 `onContactSyncFinish`，但不影响登录主链路。测试可使用 `https://download-sdk.oss-cn-beijing.aliyuncs.com/downloads/lxm/dns.json`。

### Session 2026-03-25

- Q: 初始化参数 `enableAutoSyncContacts` 是否改名？ → A: 当前阶段保持现状，不改名。
- Q: 主消息 websocket 重连成功后是否重新触发联系人预检？ → A: 不触发；仅当一轮联系人同步已经开始且同步 websocket 中途断开时，才在同一轮同步内基于已确认的 `cursor` 续传剩余分页。
- Q: 私有化直连配置里的 4 个 URL 是否应该收敛成一个结构？ → A: 应收敛成一个结构，统一承载主链路 REST/WS 与同步链路 REST/WS；同步链路字段命名不带 `contact` 前缀，以便后续复用到其他同步业务。
- Q: `getContacts()` 的返回结构是否调整？ → A: 调整为新结构 `Contact { userId, userInfo, remark, addTs }`；其中 `userInfo` 直接复用统一 `UserInfo`，至少包含 `userId`、`nickname`、`avatarUrl`、`ext` 等用户属性。
- Q: `onContactSyncFinish` 是否继续暴露 `changed`？ → A: 不暴露；只要一轮实际同步已经启动并成功完成，就必须派发 `onContactSyncFinish`，不得因为“无变更”吞掉完成事件。
- Q: 当 metadata 预检结果为“不需要同步”时，是否派发联系人同步事件？ → A: 也要派发；当前统一要求每轮联系人同步流程都形成 `onContactSyncStart -> onContactSyncFinish` 闭环，metadata 预检 `skip` 也不例外。
- Q: 联系人同步失败时是否需要额外重试？ → A: 需要；除单轮中的候选 URL 切换外，还要支持一次整轮同步级别的额外重试。
- Q: metadata 预检失败是否都走降级同步？ → A: 至少对明确的 `401/403/404` 预检失败直接派发带 `error` 的 `onContactSyncFinish`；其他失败在方案中按改动量与稳定性优先做保守设计。

## User Scenarios & Testing _(mandatory)_

### User Story 1 - 登录后自动获取最新联系人列表 (Priority: P1)

作为 SDK 使用者，我希望在初始化时显式控制是否启用“登录后自动同步联系人”，并在启用后让联系人数据从本地已知状态更新到服务端最新状态，这样联系人页无需手动触发刷新即可展示可用结果，同时不影响默认接入成本。

**Why this priority**: 自动同步联系人是联系人模块的基础价值，但它也引入额外链路与存储开销，因此必须允许业务按初始化配置显式开启。缺少这一能力或缺少开关都会影响接入可控性。

**Independent Test**: 分别验证“初始化时未开启联系人自动同步”和“初始化时开启联系人自动同步”两种场景；开启时登录后可先得到当前可用联系人结果并在自动同步完成后得到最新联系人结果，关闭时不会自动建立联系人同步流程。

**Acceptance Scenarios**:

1. **Given** 初始化时未开启联系人自动同步，**When** 用户完成登录，**Then** SDK 不会自动启动联系人同步，也不会自动建立额外联系人同步链路。
2. **Given** 初始化时已开启联系人自动同步且本地联系人缓存完整，**When** SDK 进入联系人同步阶段，**Then** 调用方可以先获得本地联系人结果，并在同步完成后获得最新联系人结果。
3. **Given** 初始化时已开启联系人自动同步且本地联系人缓存缺失或不完整，**When** SDK 首次执行联系人同步，**Then** SDK 会直接拉取完整联系人结果并保存为后续可复用状态。
4. **Given** 初始化时已开启联系人自动同步且服务端联系人列表自上次同步后有新增、删除或状态变化，**When** 自动同步完成，**Then** SDK 输出的联系人结果与服务端保持一致，且不会保留已失效联系人。
5. **Given** 初始化时已开启联系人自动同步但 DNS 未返回 `sync-ws` 或联系人同步 DNS 解析失败，**When** 用户完成登录，**Then** 登录主链路仍然成功，SDK 会派发 `onContactSyncStart` 与带 `error` 的 `onContactSyncFinish`，并输出可诊断告警日志。

### User Story 2 - 同步过程中断线后基于 cursor 续传联系人分页 (Priority: P1)

作为 SDK 使用者，我希望在自动同步已经开始后，如果联系人同步 websocket 中途断开，SDK 能在同一轮同步内基于已确认的 `cursor` 继续拉取剩余分页，并在同步完成后及时关闭本轮联系人同步链路，这样联系人数据不会因为中途断线被迫整轮重来，也不会一直占用额外连接。

**Why this priority**: 联系人同步的主要成本集中在分页拉取与结果合并。如果同步过程中一旦断线就只能从头开始，会放大耗时与失败概率；而如果链路不及时关闭，又会引入不必要的资源占用。

**Independent Test**: 在首次同步已经返回部分分页后，模拟联系人同步 websocket 中途断线、同轮恢复续传、增量新增、删除触发全量，以及最终成功关闭链路，验证 SDK 能基于 `cursor` 继续拉取剩余分页并得到正确联系人结果。

**Acceptance Scenarios**:

1. **Given** 用户已完成一次联系人同步且本地保存了联系人版本号，**When** SDK 在登录后先查询服务端联系人版本元数据，**Then** SDK 能判断本地联系人结果是否需要继续同步。
2. **Given** 用户已完成一次联系人同步且本地保存了上次同步时间戳，**When** 服务端识别到联系人版本号不一致，**Then** 服务端可按上次同步时间戳返回发生变化的联系人集合，SDK 合并后得到最新联系人结果。
3. **Given** 服务端产生联系人新增或删除，**When** 自动同步执行，**Then** SDK 会以最新联系人版本号为准更新联系人结果，并保存新的版本号。
4. **Given** 联系人同步网关返回分页结果且响应中仍带有 `cursor`，**When** SDK 继续处理本轮同步，**Then** SDK 会继续请求后续分页，直到没有新的 `cursor` 为止。
5. **Given** 联系人同步 websocket 已经拿到前几页结果并记录了最新 `cursor`，**When** 同一轮同步过程中 websocket 中途断开，**Then** SDK 必须在恢复后继续使用已确认的 `cursor` 续传剩余分页，而不是从 `cursor: 0` 整轮重来。
6. **Given** 联系人同步 websocket 在同一轮同步中断开过一次，**When** SDK 触发整轮重试，**Then** 除候选 URL 切换外，还会额外再尝试一次整轮同步，以降低单地址场景下的偶发失败率。
7. **Given** metadata 预检明确返回 `401/403/404`，**When** SDK 结束本轮预检，**Then** 会直接派发联系人同步失败事件，而不是继续发起联系人同步 websocket。
8. **Given** 用户已退出登录，**When** 联系人同步链路尚有未完成任务，**Then** SDK 会停止当前用户的联系人同步过程，并在下一次新用户登录后以新用户状态重新开始。

### User Story 3 - 联系人变化可被业务稳定感知 (Priority: P2)

作为 SDK 使用者，我希望联系人同步过程和结果变化能以稳定、可判断来源的事件被业务感知，这样联系人页、选择器和依赖联系人关系的功能可以自动刷新，而不需要持续轮询。

**Why this priority**: 自动同步只有在变化可被消费时才真正产生业务价值。缺少稳定通知机制，业务层仍需要频繁主动查询，自动同步收益会被抵消。

**Independent Test**: 完成一次初始同步，并触发同步开始、同步成功、同步失败、新增联系人、联系人删除和无变更场景，验证业务侧可以按事件观察本轮同步状态，并区分“来自本地已有结果”和“来自最新同步结果”的联系人更新。

**Acceptance Scenarios**:

1. **Given** SDK 即将开始一轮联系人自动同步，**When** 同步流程开始执行，**Then** 业务侧会收到不携带 payload 的 `onContactSyncStart` 事件。
2. **Given** SDK 已启动一轮联系人同步流程，**When** 自动同步成功结束，**Then** 业务侧会收到不携带 payload 的 `onContactSyncFinish` 事件，并可通过 `getContacts()` 获取完整最新结果。
3. **Given** 自动同步没有发现联系人变化，**When** 本轮同步结束，**Then** SDK 不会重复派发等价联系人数据更新，但仍会派发一次成功语义的 `onContactSyncFinish`。
4. **Given** 联系人同步过程中发生失败，**When** 本轮同步结束，**Then** 业务侧会收到仅携带 `error` 的 `onContactSyncFinish` 事件。
5. **Given** metadata 预检结果为“不需要同步”，**When** SDK 结束本轮预检判断，**Then** 仍会派发一次 `onContactSyncStart` 与一次不携带 payload 的 `onContactSyncFinish`。

### Edge Cases

- 用户首次登录且服务端联系人列表为空时，SDK 仍需完成同步闭环，并明确输出“空联系人结果”而不是停留在加载态。
- 本地保存的同步状态缺失、损坏或与当前用户不匹配时，SDK 需放弃旧状态并重新建立当前用户的联系人结果。
- 本地联系人关系缓存存在，但联系人资料缓存已被淘汰导致联系人结果不完整时，SDK 需显式标记“缓存不完整”，并在下一次同步时走完整联系人拉取。
- 登录后短时间内连续触发多次联系人同步或同步链路抖动时，SDK 不应并发执行多个联系人同步流程。
- 联系人自动同步关闭时，即使业务侧后续注册联系人同步事件，也不应自动收到任何联系人同步开始或完成事件。
- DNS 配置缺少 `sync-ws` 或联系人同步 DNS 解析失败时，SDK 不应让登录主链路失败，而应以 `start -> finish(error)` 的方式结束本轮自动联系人同步。
- 服务端版本元数据返回“无需同步”，但本地缓存不完整时，SDK 仍需强制同步全部联系人。
- 联系人同步网关返回多页结果且中途 cursor 断裂、重复或缺失时，SDK 需能够识别当前同步不可继续并返回可诊断失败结果。
- 联系人同步网关连接建立后若长时间无响应，SDK 需处理 ping/pong 或等价探活失败，避免同步流程悬挂。
- 服务端返回“没有新变更”时，SDK 不应覆盖已有联系人结果或重复派发联系人数据更新，但若本轮实际同步已开始，仍需派发一次成功完成事件。
- 同步进行中用户主动登出、切换账号或登录态失效时，旧用户的联系人结果与同步状态不得污染新用户。
- 联系人变更中同时存在新增、删除和属性更新时，SDK 输出的最终联系人结果必须是单一一致快照，而不是部分更新后的中间状态。
- 联系人同步完成后，应及时关闭本轮联系人同步链路，避免额外连接长期占用。

## Requirements _(mandatory)_

### Functional Requirements

- **FR-001**: 系统必须在初始化配置中提供联系人自动同步开关，默认值为关闭。
- **FR-002**: 当联系人自动同步开关关闭时，系统不得在登录成功后自动启动联系人同步流程，也不得自动建立联系人同步链路。
- **FR-003**: 当联系人自动同步开关开启时，系统必须在用户登录成功后自动启动当前用户的联系人预检与同步决策流程，不要求业务侧显式触发首次同步。
- **FR-004**: 系统必须按当前登录用户隔离联系人结果、同步状态和本地保存信息，不得发生不同账号之间的数据串用。
- **FR-005**: 对外联系人数据模型必须采用 `Contact { userId, userInfo, remark, addTs }` 结构；其中 `userInfo` 必须直接复用统一 `UserInfo`，至少包含 `userId`、`nickname`、`avatarUrl`、`ext` 等用户属性。
- **FR-006**: 系统必须使用联系人版本号管理联系人集合本身的变化；当联系人新增或删除导致集合发生变化时，必须以新的联系人版本号作为最新集合状态标识。
- **FR-007**: 系统必须使用上次同步时间戳识别联系人资料变化；当联系人资料在上次同步后发生变化时，系统必须能够基于该时间戳同步变化联系人的完整资料。
- **FR-008**: 仅当当前用户的本地联系人缓存被判定为完整时，系统才可以优先提供本地联系人结果，并在后续同步完成后提供最新联系人结果。
- **FR-009**: 当不存在可用本地联系人结果，或本地联系人缓存被判定为不完整时，系统必须执行一次完整联系人获取流程，并在完成后生成当前用户的初始联系人结果。
- **FR-010**: 系统必须同时保存联系人版本号、上次同步时间戳以及缓存完整性状态，使下一轮同步可以基于已知进度继续追平，而不是默认重复全量处理。
- **FR-011**: 系统必须在用户登录成功后执行联系人追平流程；若一轮联系人同步已经开始且同步 websocket 中途断开，系统必须在同一轮同步内基于已确认的 `cursor` 继续追平剩余分页。
- **FR-012**: 同一用户在任意时刻只允许存在一个进行中的联系人同步流程；重复触发时必须合并或忽略后续重复请求，避免并发污染结果。
- **FR-013**: 当同步结果与当前联系人结果完全一致时，系统不得重复输出等价联系人结果或重复派发联系人数据更新通知。
- **FR-014**: 当同步发现联系人新增、删除或状态变化时，系统必须产出一个完整、已合并的最新联系人结果，而不是要求业务侧自行拼接局部变更。
- **FR-015**: 系统必须向业务侧提供联系人同步状态通知与联系人读取入口；业务侧通过 `getContacts()` 读取当前最新联系人结果，联系人同步事件本身不直接回传联系人数据。
- **FR-016**: 系统必须对外提供 `onContactSyncStart` 与 `onContactSyncFinish` 两个联系人同步事件。
- **FR-017**: 当联系人自动同步开启且一轮联系人同步流程被触发时，系统必须始终派发一次不携带 payload 的 `onContactSyncStart`。
- **FR-017a**: 每轮联系人同步流程结束时，系统必须始终派发一次 `onContactSyncFinish`；成功时不携带 payload，失败时仅携带 `error`，不得因为 `skip`、无业务变化或快速失败而吞掉完成事件。
- **FR-018**: 同步过程中若当前用户登出、切换账号或登录态失效，系统必须停止旧用户的同步流程，并清理旧流程的后续输出资格。
- **FR-019**: 当本地保存的联系人状态缺失、损坏、不可识别或与当前用户不匹配时，系统必须丢弃该状态并重新建立当前用户的联系人同步基线。
- **FR-020**: 系统必须在联系人列表为空时仍然完成同步成功闭环，并输出可识别的空联系人结果。
- **FR-021**: 系统必须保证联系人结果在一次同步完成后处于一致快照状态，不得让业务侧观察到只更新一部分联系人的中间结果。
- **FR-022**: 系统必须为联系人同步失败提供可诊断结果，使业务侧能够识别“仍可使用旧结果”和“当前没有可用联系人结果”两类状态差异。
- **FR-023**: `onContactSyncFinish` 在失败时携带的 `error` 必须区分失败阶段，至少能表达 `metadata`、`socket_connect`、`sync_page`、`decode`、`cancelled` 等阶段语义；阶段信息可以直接编码在错误消息文本中。
- **FR-024**: 当联系人自动同步开启时，系统必须在登录后先查询服务端联系人版本元数据，用于判断本轮是否需要继续同步联系人数据。
- **FR-025**: 当服务端版本元数据判断“需要同步”或本地缓存被标记为不完整时，系统必须继续执行联系人同步。
- **FR-026**: 当服务端识别到联系人版本号不一致，且变化仅涉及“新增联系人或资料更新”时，系统必须支持基于上次同步时间戳同步变化部分的联系人完整资料，并在同步完成后更新本地联系人版本号与时间戳。
- **FR-027**: 当服务端版本元数据判断“不需要同步”且本地缓存完整时，系统可以跳过本轮联系人数据同步，但仍必须按统一 contract 派发 `onContactSyncStart -> onContactSyncFinish`。
- **FR-028**: 当服务端版本元数据判断“不需要同步”但本地缓存不完整时，系统仍必须执行一次完整联系人同步，保证联系人结果完整。
- **FR-029**: 当联系人新增通知携带最新联系人版本号时，系统必须记录该版本号，并允许后续通过增量同步补齐新增联系人。
- **FR-030**: 当联系人删除导致联系人集合发生变化时，系统必须执行一次完整联系人同步，不得依赖“仅返回变化部分”的增量结果推断删除。
- **FR-031**: 当联系人版本元数据查询明确返回 `401/403/404` 时，系统必须以 `onContactSyncStart -> onContactSyncFinish(error)` 结束本轮流程，不得继续发起联系人同步 websocket。
- **FR-032**: 当联系人版本元数据查询出现其他失败时，系统必须采用稳定性优先的保守策略处理，并保证失败结果可诊断且不影响登录主链路；具体是否允许有限重试由实施方案定义。
- **FR-033**: 联系人自动同步开启时，系统可以在同步阶段建立专用联系人同步链路；当本轮同步完成或失败终止后，必须关闭该链路，不得默认长期保持。
- **FR-034**: 当前阶段的联系人本地存储必须参考 `014` 的本地缓存约束，并按用户维度隔离。
- **FR-035**: 联系人本地存储不得为 `nickname` 与 `avatarUrl` 额外保留第二份持久化副本；联系人完整展示结果应由联系人关系数据与用户资料缓存数据在运行时合并得到。
- **FR-036**: 联系人本地存储中，`remark`、`addTs`、联系人版本号、上次同步时间戳、缓存完整性状态以及联系人关系结果必须保留在联系人域存储中，不得仅依赖用户信息缓存推导。
- **FR-037**: 若当前阶段不扩展现有用户信息缓存字段，则 `sign` 必须留在联系人域存储中；若后续扩展用户信息缓存支持 `sign`，需保证联系人读取语义保持兼容。
- **FR-038**: 当联系人关系缓存存在但关联的用户资料缓存缺失、损坏或被淘汰，导致无法拼出完整联系人结果时，系统必须把本地联系人缓存标记为不完整。
- **FR-039**: 联系人专用同步链路必须使用独立的二进制自定义协议，至少支持探活请求/响应、联系人同步请求/响应以及错误结果表达。
- **FR-039a**: 联系人同步 websocket 客户端必须抽象出可复用的 sync transport 层，避免接口语义绑定“仅同步联系人”，以便后续承载更多同步数据类型并支持长连接演进。
- **FR-040**: 联系人同步响应必须同时支持“全量结果”和“增量结果”两种语义，并允许通过分页 cursor 连续返回多页联系人数据，直到本轮同步结束。
- **FR-040a**: 当联系人同步 websocket 在本轮同步中途断开后重新建立连接时，系统必须复用当前轮次已确认的 `cursor` 继续拉取剩余分页，而不是默认从 `cursor: 0` 重新开始。
- **FR-041**: 当前阶段联系人同步所依赖的 protobuf 协议必须仿照现有消息协议使用静态生成产物，运行时不得依赖动态解析 `.proto` 文本作为主路径。
- **FR-042**: 联系人同步请求必须能够携带当前用户身份、当前已知联系人版本号以及分页 cursor，使服务端能够返回正确的全量或增量结果。
- **FR-043**: 联系人同步 websocket 地址在可用时必须来源于 DNS 配置中的 `sync-ws` 字段，且该字段支持多个候选地址。
- **FR-044**: 当 `sync-ws` 返回多个候选地址时，系统在本轮连接尝试前应先对地址列表做随机化处理；某个地址连接失败后，必须按剩余候选顺序切换到下一个地址继续尝试。
- **FR-044a**: 当业务在私有化直连场景下显式传入地址配置时，系统必须支持以一个结构统一承载主链路 REST/WS 与同步链路 REST/WS 四类地址，且同步链路字段命名不得绑定 `contact` 语义，便于后续复用。
- **FR-045**: 当前阶段的实现范围必须仅限于联系人自动同步、联系人结果缓存、同步状态推进与更新通知，不包含新增好友、删除好友、同意申请、拒绝申请等联系人操作 API。
- **FR-046**: 系统必须为后续补充联系人操作 API 保留兼容边界，当前阶段定义的联系人结果、同步状态和更新通知语义在后续阶段不得被破坏性重写。
- **FR-047**: 联系人同步响应中的 `RosterItem.metadata` 必须能够承载 `nickname`、`avatarUrl`、`sign`，SDK 在处理联系人同步页时必须直接解析这些字段，并同步回写/更新现有 `userInfo` 缓存。
- **FR-048**: 当联系人自动同步开启但 DNS 缺少 `sync-ws`、或为自动同步补拉 DNS 失败时，系统必须记录可诊断的告警日志，并以 `onContactSyncStart -> onContactSyncFinish(error)` 结束本轮自动联系人同步，不得让登录主链路失败。

### Key Entities _(include if feature involves data)_

- **ContactRecord**: 联系人记录实体，表示某个联系人在当前账号下的可展示结果，包含联系人身份、`userInfo` 投影、备注与建联时间。
- **ContactSnapshot**: 联系人快照实体，表示某一时刻当前用户完整、可消费的联系人结果集合。
- **ContactSyncCheckpoint**: 联系人同步检查点实体，表示当前用户上一次已确认的同步进度，用于后续继续追平联系人变更。
- **ContactVersionState**: 联系人版本状态实体，表示当前用户已知的联系人集合版本号，用于判断联系人数量是否发生变化。
- **ContactCacheMeta**: 联系人缓存元数据实体，表示当前联系人缓存是否完整、最近一次成功同步状态以及是否需要在下一次登录时执行完整联系人拉取。
- **ContactSyncResult**: 联系人同步输出实体，表示一次同步完成后的结果，包含联系人快照、结果来源、是否发生变化以及失败时的状态说明。
- **ContactProfileProjection**: 联系人展示投影实体，表示联系人关系字段与用户资料字段合并后的展示结果；其中 `userInfo` 来自用户资料缓存或同步结果，`remark` 与 `addTs` 保留在联系人域。
- **RosterSyncPage**: 联系人同步分页结果实体，表示一页联系人同步数据，包含联系人列表、版本号、响应类型以及后续 cursor。

### Assumptions & Dependencies

- 当前阶段只交付“联系人自动同步”能力，原工程中的联系人操作 API 补齐属于后续阶段，不纳入本期实现与验收。
- 服务端提供可用于首次获取联系人结果与后续继续追平联系人变更的稳定能力，并支持判定“当前没有新变更”。
- 服务端提供联系人版本元数据查询能力，SDK 可在登录后先基于该结果判断本轮是否需要继续同步。
- 联系人版本元数据查询明确返回 `401/403/404` 时，客户端直接结束本轮并派发带 `error` 的完成事件；其他查询失败按实施方案中的稳定性优先策略处理。
- 服务端通过联系人版本号反映联系人集合人数变化，通过上次同步时间戳筛选资料发生变化的联系人，并在必要时返回这些联系人的完整资料。
- 服务端通过联系人版本号反映联系人集合人数变化；新增联系人允许通过增量同步补齐，删除联系人时客户端改走全量同步，不依赖增量结果推断删除。
- 联系人同步网关通过独立 protobuf 自定义协议传输联系人分页结果，支持全量/增量两种响应类型与 cursor 连续分页。
- 联系人同步 websocket 地址在可用时来源于 DNS 配置中的 `sync-ws`；若该字段缺失或自动同步补拉 DNS 失败，则自动联系人同步按降级路径记录告警，并以带错误的完成事件结束。测试环境可使用 `https://download-sdk.oss-cn-beijing.aliyuncs.com/downloads/lxm/dns.json` 获取样例配置。该 URL 未在本次澄清中进一步校验，后续联调前应实测确认字段格式。
- 联系人同步页中的 `RosterItem.metadata` 可直接提供 `nickname/avatarUrl/sign`，SDK 在同步时可据此回填用户资料缓存，而不要求额外串联一轮 userInfo 查询。
- 业务侧至少需要一种读取当前联系人结果和感知联系人同步状态的公开入口；联系人同步事件本身不直接承载联系人列表，业务侧通过 `getContacts()` 主动读取最新结果。
- 当前阶段允许联系人结果依赖本地持久化或等价缓存机制提升登录后可用性；具体缓存介质在方案设计中确定。
- 当前已有用户信息缓存仅稳定覆盖 `nickname` 与 `avatarUrl`，不天然覆盖联系人关系字段；因此联系人域仍需保留自身关系数据与同步元信息，并在资料缓存缺失时把联系人缓存标记为不完整。
- 若 demo 侧尚未提供联系人展示入口，本期 E2E 可先以“待评估”方式记录，并由集成测试覆盖联系人自动同步主链路。

## Success Criteria _(mandatory)_

### Measurable Outcomes

- **SC-001**: 在联系人自动同步关闭的账号场景下，登录流程不会自动启动联系人同步，误触发率为 0。
- **SC-002**: 在联系人自动同步开启且存在本地联系人结果的账号下，登录后业务侧可在一次登录流程内先获得当前可用联系人结果，并在后续自动获得最新联系人结果，成功率达到 100%。
- **SC-003**: 在首次登录且无本地联系人结果的账号下，联系人自动同步完成后可得到完整联系人结果或空联系人结果，成功率达到 100%。
- **SC-004**: 在登录后先查询联系人版本元数据的场景下，SDK 对“跳过同步 / 增量同步 / 强制全量同步”三种路径的判定正确率达到 100%。
- **SC-005**: 在联系人同步 websocket 中途断开但同轮允许续传的场景下，SDK 可基于已确认的 `cursor` 继续追平剩余分页，且最终联系人结果与服务端一致，正确率达到 100%。
- **SC-006**: 在“无联系人变化”的同步场景下，SDK 不产生重复等价更新通知，重复通知率为 0。
- **SC-007**: 在账号切换、登出或登录态失效场景下，旧用户联系人结果不污染新用户，跨账号串用率为 0。
- **SC-008**: 在同步状态缺失、损坏或不可用场景下，SDK 可自动回退到可恢复路径并重新建立联系人结果，恢复成功率达到 100%。
- **SC-009**: 在联系人自动同步开启场景下，每轮联系人同步结束后联系人同步链路都会被关闭，未关闭残留率为 0。
- **SC-010**: 在联系人同步网关返回多页结果的场景下，SDK 可连续完成分页拉取并正确合并全量/增量结果，分页遗漏率与重复率均为 0。
