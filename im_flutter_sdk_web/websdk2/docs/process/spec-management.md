# Spec 文档管理最佳实践

## 一、累积 Spec 的价值和作用

### 1.1 核心价值

累积的 spec 文档有以下重要作用：

#### 📚 **知识库和上下文**
- **AI 上下文增强**：AI 可以读取所有 spec 文档，理解项目的完整演进历史和设计决策
- **新成员 onboarding**：新开发者可以通过 spec 快速了解功能的设计思路和实现方案
- **设计决策追溯**：记录"为什么这样设计"，避免重复讨论和错误决策

#### 🔍 **问题排查和调试**
- **历史参考**：遇到类似问题时，可以查看历史 spec 了解之前的解决方案
- **依赖关系**：理解功能之间的依赖关系，避免破坏性变更
- **测试场景**：保留历史测试场景，确保回归测试完整

#### 📈 **项目演进记录**
- **架构演进**：记录架构如何从简单到复杂，为什么演进
- **技术选型**：记录技术选型的原因和替代方案考虑
- **经验积累**：将"踩过的坑"和"最佳实践"沉淀为文档

### 1.2 实际使用场景

```typescript
// 场景 1: AI 理解上下文
// 当你在新功能中需要参考旧功能时，AI 可以读取相关 spec
// 例如：新功能需要复用旧功能的错误处理逻辑

// 场景 2: 代码审查
// 审查者可以查看 spec 了解设计意图，而不是只看代码实现

// 场景 3: 重构决策
// 重构时查看历史 spec，了解哪些功能依赖当前实现
```

## 二、何时需要详细 Spec，何时不需要

### 2.1 需要详细 Spec 的场景 ✅

#### **大型功能/重构**
- 涉及多个模块的改动
- 影响现有 API 的变更
- 需要团队讨论和评审的功能

**示例**：
- `001-im-sdk-refactor` - 整个 SDK 重构
- `002-rest-api-v3-upgrade` - REST API 升级
- `003-message-protocol-redesign` - 消息协议重新设计

#### **复杂业务逻辑**
- 涉及复杂状态机
- 需要处理多种边界情况
- 性能要求高的功能

**示例**：
- `010-offline-message-sync` - 离线消息同步（复杂状态管理）
- `015-multi-tab-coordination` - 多标签页协调（复杂同步逻辑）

#### **需要长期维护的功能**
- 核心功能，会持续迭代
- 需要文档化的公共 API
- 需要向后兼容的功能

### 2.2 不需要详细 Spec 的场景 ❌

#### **简单 Bug 修复**
```bash
# 不需要创建 spec，直接在代码中注释说明即可
// Fix: 修复消息去重逻辑，处理并发场景下的重复消息
```

#### **代码重构（不改变行为）**
```bash
# 不需要 spec，在 PR 描述中说明即可
# Refactor: 提取消息验证逻辑到独立函数，提高可测试性
```

#### **细节实现**
```typescript
// ❌ 不需要写 spec 的细节：
// "如果 ignoreMyOwnMsg 为 true，且消息来自当前用户，且是聊天室消息，则丢弃"

// ✅ 代码注释即可：
if (
  ignoreMyOwnMsg &&
  meta.from &&
  meta.from.name === this.context.userId &&
  meta.from.clientResource === this.clientResource &&
  thirdMessage.type === MsyncMessageType.CHATROOM
) {
  return logger.debug('Discard your own chat room message:', msgId);
}
```

#### **配置调整**
```bash
# 不需要 spec，在 CHANGELOG 中记录即可
# Chore: 更新构建配置，优化打包体积
```

## 三、Spec 管理策略

### 3.1 分层管理

```
specs/
├── 001-im-sdk-refactor/          # 大型重构（保留）
│   ├── spec.md                   # 详细需求
│   ├── plan.md                   # 详细方案
│   └── tasks.md                  # 详细任务
│
├── 002-rest-api-v3/              # 重要功能（保留）
│   └── spec.md                   # 简化版（只保留关键决策）
│
├── 010-offline-sync/             # 复杂功能（保留）
│   └── spec.md                   # 详细设计
│
└── archived/                     # 归档目录
    ├── 005-bug-fix-xxx/          # Bug 修复（归档）
    ├── 006-refactor-xxx/          # 简单重构（归档）
    └── 007-config-update/        # 配置调整（归档）
```

### 3.2 精简策略

#### **策略 1: 只保留关键决策**
```markdown
# 精简版 spec.md（只保留关键信息）

## 关键决策
- 使用管理器模式而非函数式 API（原因：开发体验更好）
- 使用 protobufjs-lite 而非完整版（原因：减小体积）

## 依赖关系
- 依赖 User Story 1（连接和消息功能）

## 测试场景
- 验证 tree shaking 生效
```

#### **策略 2: 合并相关功能**
```bash
# 将多个小功能合并到一个 spec
specs/002-api-improvements/
├── spec.md          # 包含：参数校验、错误处理、REST v3 升级
└── plan.md          # 统一的技术方案
```

#### **策略 3: 定期归档**
```bash
# 每季度归档一次
# 将已完成的、不再需要参考的 spec 移到 archived/
# 只保留正在开发和需要长期维护的 spec
```

### 3.3 自动化管理

#### **创建归档脚本**
```bash
# .specify/scripts/bash/archive-specs.sh
# 自动归档已完成且超过 6 个月的 spec
```

#### **Spec 清理检查清单**
```markdown
- [ ] 功能是否已完成并合并到主分支？
- [ ] 是否还有代码依赖这个 spec 的设计？
- [ ] 是否包含重要的设计决策需要保留？
- [ ] 是否超过 6 个月未更新？
- [ ] 是否可以精简为关键决策摘要？
```

## 四、最佳实践建议

### 4.1 分层记录原则

```
┌─────────────────────────────────────┐
│  Constitution (原则)                │  ← 长期保留，很少变化
├─────────────────────────────────────┤
│  Spec (需求)                         │  ← 大型功能保留，小功能归档
├─────────────────────────────────────┤
│  Plan (方案)                         │  ← 复杂方案保留，简单方案归档
├─────────────────────────────────────┤
│  Tasks (任务)                        │  ← 完成后可归档
├─────────────────────────────────────┤
│  代码注释 (实现细节)                 │  ← 细节在这里，不在 spec
└─────────────────────────────────────┘
```

### 4.2 推荐做法

#### ✅ **应该做的**

1. **大型功能写详细 spec**
   - 重构、新模块、复杂功能
   - 需要团队讨论的功能

2. **关键决策记录在 spec**
   - 为什么选择这个方案
   - 替代方案为什么被拒绝
   - 性能/安全考虑

3. **定期归档旧 spec**
   - 每季度归档一次
   - 只保留活跃和重要的 spec

4. **代码细节写在代码注释**
   - 实现细节不需要 spec
   - 业务逻辑注释在代码中

#### ❌ **不应该做的**

1. **不要为每个小改动写 spec**
   - Bug 修复不需要
   - 简单重构不需要
   - 配置调整不需要

2. **不要在 spec 中写实现细节**
   ```markdown
   ❌ 错误示例：
   - 如果 ignoreMyOwnMsg 为 true，且消息来自当前用户...
   
   ✅ 正确做法：
   - 实现消息去重逻辑（细节在代码注释中）
   ```

3. **不要保留所有历史 spec**
   - 归档已完成且不再需要的
   - 精简为关键决策摘要

### 4.3 效率平衡

#### **效率对比**

| 场景 | 详细 Spec | 精简 Spec | 代码注释 | 推荐 |
|------|----------|----------|---------|------|
| 大型重构 | ✅ | ❌ | ❌ | 详细 Spec |
| 复杂功能 | ✅ | ⚠️ | ❌ | 详细 Spec |
| 简单功能 | ❌ | ✅ | ⚠️ | 精简 Spec |
| Bug 修复 | ❌ | ❌ | ✅ | 代码注释 |
| 实现细节 | ❌ | ❌ | ✅ | 代码注释 |

#### **时间分配建议**

```
100% 开发时间分配：
├── 70% 写代码（包含代码注释）
├── 20% 写详细 spec（大型功能）
├── 5%  写精简 spec（简单功能）
└── 5%  维护和归档 spec
```

## 五、实际操作建议

### 5.1 当前项目建议

基于你的项目情况（`001-im-sdk-refactor`），建议：

1. **保留当前 spec** ✅
   - 这是大型重构，需要详细记录
   - 包含重要的架构决策
   - 后续功能可能依赖这个设计

2. **后续功能分层处理**：
   ```bash
   # 大型功能（写详细 spec）
   specs/002-group-management/        # 群组管理（复杂）
   specs/003-push-notification/       # 推送通知（复杂）
   
   # 中型功能（写精简 spec）
   specs/010-avatar-display/         # 头像显示（简单）
   specs/011-message-search/          # 消息搜索（中等）
   
   # 小功能（不写 spec，代码注释）
   # Bug 修复、简单重构、配置调整
   ```

3. **定期归档**：
   ```bash
   # 每季度执行一次
   # 将已完成且超过 6 个月的 spec 归档
   mv specs/005-xxx archived/
   ```

## 六、总结

### 核心原则

1. **分层记录**：原则 → 需求 → 方案 → 任务 → 代码注释
2. **按需详细**：大型功能详细，小功能精简，细节在代码
3. **定期归档**：保留活跃和重要的，归档已完成和过时的
4. **效率平衡**：不要过度文档化，也不要缺乏文档

### 回答你的问题

**Q: 累积的 spec 会不会太多？**
A: 会，但可以通过归档和精简管理。建议只保留：
- 正在开发的功能
- 需要长期维护的功能
- 包含重要设计决策的功能

**Q: 一直积累有什么作用？**
A: 主要作用：
- AI 上下文增强（理解项目演进）
- 知识库（新成员 onboarding）
- 设计决策追溯（避免重复讨论）
- 问题排查（历史参考）

**Q: 细节一直写 spec 效率不高？**
A: 对！**细节应该在代码注释中，不在 spec**。Spec 应该记录：
- ✅ 为什么（设计决策）
- ✅ 做什么（功能需求）
- ❌ 怎么做（实现细节，应该在代码注释中）
