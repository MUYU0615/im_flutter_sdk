# 测试架构说明

## 1. 文档目标

本文档用于说明 `websdk2` 当前测试体系的架构视角，重点回答以下问题：

- 哪些属于测试领域常见的标准分层
- 哪些属于 TypeScript / SDK 工程中的专项测试
- 哪些属于 CI / 发布流程中的执行门禁
- 当前仓库目录如何映射到这三类概念

本文档描述的是“测试架构”，不是简单按文件夹罗列测试目录。目录组织会随着工程演进调整，但测试架构应保持稳定、可沟通、可扩展。

## 2. 总体模型

当前工程建议用“三段式”理解测试体系：

```text
标准测试分层
├── Unit
├── Integration
└── E2E

专项测试
├── Contract
└── Type

执行门禁
├── PR Gate
├── Nightly Gate
└── Release Gate
```

这意味着仓库里的测试并不是“6 个并列测试层”，而是：

- 3 个标准主层：单元、集成、端到端
- 2 个专项验证域：契约、类型
- 1 组执行策略：PR / Nightly / Release 门禁

## 3. 标准测试分层

### 3.1 单元测试（Unit Test）

单元测试用于验证单个函数、类或模块在隔离条件下的行为正确性。

特点：

- 执行快
- 定位问题精确
- 更适合覆盖纯逻辑、错误分支、边界条件
- 通常通过 mock / fake 隔离网络、存储、时钟等外部依赖

在本工程中的主要职责：

- 消息编解码逻辑
- 连接管理与重试策略
- 管理器层行为
- 平台适配层行为
- 上传、缓存、错误映射等基础模块

目录映射：

- `tests/unit`

### 3.2 集成测试（Integration Test）

集成测试用于验证多个模块组合后的协作行为是否正确，关注“模块之间是否能按约定协同工作”。

特点：

- 比单元测试更接近真实链路
- 允许保留部分真实依赖或高保真 mock
- 更适合验证协议边界、时序问题、状态机联动

在本工程中的主要职责：

- WebSocket + protobuf 协议交互
- SDK 与 mock server 的消息收发链路
- 连接建立、ACK、下行消息、异常断连等联动

目录映射：

- `tests/integration`

说明：

- 当前工程的集成测试只保留本地可控场景：
- mock server 场景：覆盖协议主链路、异常链路和时序回归场景
- local-only 场景：覆盖缓存、多模块协作等不依赖真实后端的组合行为

### 3.2.1 单元测试与集成测试的职责边界

单元测试和集成测试不是“谁更高级”的关系，而是分别回答两类不同问题：

- 单元测试回答：某个函数、类或模块自身是否正确
- 集成测试回答：多个模块接起来以后是否还能正确工作

在本工程中，建议按下面的职责边界理解：

单元测试重点负责：

- 参数校验、默认值、边界条件
- 错误分支、错误码映射、异常包装
- 数据转换、协议字段映射、返回值 shape
- 单个 manager / adapter / utility / codec 的内部行为正确性

集成测试重点负责：

- `ChatClient` / `CoreSDK` / manager / transport / mock server / cache / event 等模块之间的协作链路
- 关键公开能力在真实组装后的 happy path 是否可跑通
- ACK、下行消息、断连、超时、乱序、重复响应等跨模块联动场景
- “单测都通过，但模块接起来后不工作”的回归风险

公开 API 是否都需要集成测试，结论是否定的。

更合理的原则是：

- 每类关键公开能力至少要有代表性的集成测试用例
- 不是每个对外方法都必须逐个补一条集成测试
- 细粒度参数组合、错误映射矩阵、边界分支仍应主要由单元测试承担

因此，公开 API 的测试选择建议如下：

- 若 API 会跨多个模块协作，或依赖 transport / mock server / event / cache 等真实拼装链路，应补集成测试
- 若 API 主要是参数透传、简单封装、字段转换，则通常由单元测试覆盖即可
- 集成测试应优先选择“能力域代表用例”，而不是按方法名机械铺满

一句话概括：

- 单元测试追求“细”，保证零件本身正确
- 集成测试追求“通”，保证零件装起来正确

### 3.3 端到端测试（End-to-End Test / E2E）

E2E 测试从用户入口或浏览器入口出发，验证完整链路在真实运行环境下是否可用。

特点：

- 最接近真实使用方式
- 覆盖面大，但执行慢、维护成本高
- 适合验证“能不能真正跑通”，不适合承担所有细节回归

在本工程中的主要职责：

- 浏览器环境下真实 demo 页面初始化
- 登录并建立真实连接
- 页面侧消息发送、消息状态与日志可观测性
- 登出与主链路回归

目录映射：

- `tests/e2e`

### 3.4 真实环境 Smoke（Real-Env Smoke）

真实环境 smoke 用于验证 SDK 与真实测试环境的接入可用性，但它不属于当前工程的 integration gate。

特点：

- 依赖真实网络、凭证和后端可用性
- 更适合做独立 smoke 或发布前补充校验
- 不适合作为前端日常回归的基础门禁

在本工程中的主要职责：

- 校验真实 DNS / 凭证 / WebSocket 地址是否可用
- 验证真实环境核心主路径可接通
- 作为 mock-only integration 的补充，而不是替代

目录映射：

- `tests/smoke/real-env`

## 4. 专项测试

### 4.1 契约测试（Contract Test）

契约测试用于验证调用方和被调用方之间的接口约定没有被破坏。这里的“契约”不只指 OpenAPI，也包括事件载荷、门禁证据格式、关键行为约束等。

特点：

- 关注接口边界稳定性
- 适合做“回归保护网”
- 常位于集成边界附近，但不等同于普通集成测试

在本工程中的主要职责：

- 门禁编排器输出约定
- 流式消息能力边界约定
- release gate / failure evidence 相关约束
- 跨平台适配兼容性约束

目录映射：

- `tests/contract`

说明：

- 契约测试在现代工程实践里是明确的测试类型
- 但它不是所有团队都会单独列为“顶级测试层”
- 在本工程里，将其单独保留是为了保护 SDK 的外部稳定性与测试治理规则本身

### 4.2 类型测试（Type Test）

类型测试用于验证 TypeScript 类型声明、推导结果和公开 API 的类型边界是否符合预期。

特点：

- 属于 TypeScript 工程特有的专项验证
- 不属于经典测试金字塔主分层
- 对 SDK、库项目尤其重要，因为类型本身就是对外 API 的一部分

在本工程中的主要职责：

- 公开事件载荷类型约束
- 管理器使用方式约束
- 推送、流式消息等能力的类型回归

目录映射：

- `tests/types`

## 5. 执行门禁

门禁不是测试层，而是“在什么时机运行哪些测试，并决定是否允许继续合并或发布”的工程规则。

### 5.1 PR Gate

目标：

- 提供快速而有阻断力的合并前验证

当前策略：

- 跑单元测试
- 跑 mock 集成测试
- 默认不跑浏览器 E2E

命令：

- `npm run test:gate:pr`

### 5.2 Nightly Gate

目标：

- 在定时任务中执行更完整的测试集合，发现慢问题、环境问题和跨层联动回归

当前策略：

- 跑单元测试
- 跑 mock 集成测试
- 跑浏览器 E2E
- 失败时记录证据

命令：

- `npm run test:gate:nightly`

### 5.3 Release Gate

目标：

- 在发布前确保关键测试链路和最近 E2E 状态满足上线要求

当前策略：

- 跑单元测试
- 跑 mock 集成测试
- 校验 E2E 最近通过记录

命令：

- `npm run test:gate:release`

## 6. 当前仓库映射关系

```text
tests/
├── unit/         -> 标准分层：单元测试
├── integration/  -> 标准分层：集成测试
├── smoke/        -> 补充验证：真实环境 smoke
├── e2e/          -> 标准分层：端到端测试
├── contract/     -> 专项测试：契约测试
├── types/        -> 专项测试：类型测试
└── test-utils/   -> 测试基础设施，不单独算测试层
```

补充说明：

- `tests/test-utils` 是测试基础设施目录，服务于多个层级，不应被视作测试分层本身
- `test:gate:*` 是执行策略，不应与 `tests/*` 目录并列为“测试层”
- `tests/smoke` 是补充验证目录，不参与 integration 的定义和 gate 统计

## 7. 覆盖率与成熟度

当前工程已设置覆盖率门禁，`vitest.config.ts` 中要求：

- `statements >= 85`
- `branches >= 75`
- `functions >= 90`
- `lines >= 85`

从工程化角度看，当前测试成熟度已经超过“只有单元测试”的基础阶段，主要体现在：

- 有清晰的标准主层：`unit / integration / e2e`
- 有面向 SDK 边界稳定性的专项测试：`contract / types`
- 有分环境、分时机的门禁策略：`pr / nightly / release`
- mock-only integration 已覆盖 SDK 主链路，而真实环境校验通过独立 smoke 保留
- 有失败证据沉淀，便于排查 flaky 或环境问题

## 8. 边界与风险

虽然当前测试架构已经较完整，但仍需明确其边界：

- 真实环境测试当前覆盖的是核心主链路，不代表所有异常都在真环境回归
- E2E 更适合作为关键路径验证，不宜承担所有协议细节校验
- 覆盖率达标不等于时序、并发、弱网、平台差异场景已经完全无缺口
- 契约测试和类型测试更偏“边界保护”，不能替代真实链路验证

## 10. 推荐对外表述

当团队需要对外描述当前工程测试体系时，建议使用以下说法：

> 本项目采用“标准测试分层 + 专项测试 + 执行门禁”的测试架构。  
> 标准分层为单元测试、集成测试、端到端测试；专项测试包括契约测试与类型测试；PR、Nightly、Release 三类门禁负责在不同阶段运行不同测试集合并决定是否放行。
