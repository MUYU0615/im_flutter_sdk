# IM SDK Web Constitution（适配 Web SDK）

## 适用范围

本 Constitution 适用于本仓库内的 SDK 代码、测试、脚本与文档，重点约束对外 API、协议适配与工程流程。

## 技术栈

- TypeScript（strict 模式）
- zod
- protobufjs
- vitest
- vite
- eslint

## 核心原则

### I. 性能与响应性（非阻塞优先）

所有核心逻辑必须采用异步非阻塞设计，避免阻塞主线程。网络 I/O、消息处理、状态同步等关键路径必须使用 Promise/async-await。SDK 侧性能目标以基准测试与实际业务场景为准，不强制服务端式吞吐/并发硬指标，但必须避免明显性能回退与内存泄漏。

### II. 类型安全（不可妥协）

项目必须使用 TypeScript 严格模式（strict）。禁止使用 `any` 类型，特殊情况必须使用 `unknown` 并配合类型守卫。所有公共 API 必须提供完整类型定义，类型与运行时行为一致，类型即文档。

### III. 可靠性与韧性

异步操作必须有超时控制并使用 try/catch 处理错误。连接相关流程需具备断线重连能力与指数退避策略（如适用），并处理网络抖动、乱序、重复消息等异常情况。

### IV. 可扩展性与协议适配

消息协议支持 protobuf 扩展与自定义消息类型。架构需支持插件化扩展，核心功能与扩展解耦。API 设计遵循开闭原则，向后兼容优先。

### V. 可观测性与可诊断性

关键操作（连接建立、消息发送/接收、错误发生）必须记录结构化日志，日志级别可控。不得在日志中输出敏感信息（token、密码等）。
日志格式与字段规范必须遵循 `specs/012-log-report/spec.md`。

### VI. 版本与变更治理

版本号遵循语义化版本（SemVer）。公共 API 的破坏性变更必须说明迁移方案。每次修改必须更新版本号与 CHANGELOG。

## TypeScript 与代码规范

1. **类型定义**
   - 公共 API 使用 `interface`，内部类型使用 `type`。
   - 函数/方法必须显式声明返回类型。
   - 只读数据使用 `readonly`，数组使用 `ReadonlyArray<T>`。
   - 优先联合类型而非枚举，除非需要反向映射。
   - 泛型必须添加合理约束。
   - 避免滥用可选链，仅在确有 `undefined/null` 风险时使用。

2. **导入导出**
   - 仅使用命名导出，避免默认导出。
   - 导入顺序：外部库 → 内部模块 → 类型导入。
   - 类型导入使用 `import type`。

3. **类与可见性**
   - 类成员必须显式 `public/private/protected`。
   - 不可变属性使用 `readonly`。

4. **配置与常量**
   - 超时/重试等时间配置必须集中在 `src/config/timeouts.ts`，禁止在业务代码中硬编码。
   - 事件名、状态名、原因名必须集中定义为常量或联合类型，禁止在业务逻辑中直接硬编码。
5. **控制流与性能**
   - 优先使用提前返回（guard clause），减少深层嵌套并提升可读性。
   - 对同一键进行多次查找时，先构建索引映射（如 `Map`）替代重复 `.find()`。

## 异步编程规范

- 优先使用 async/await，避免 .then() 链式调用。
- 所有异步操作必须 try/catch 错误处理。
- 必须设置超时（Promise.race 或统一的超时封装）。

## 错误处理与事件系统

- 错误处理必须遵循 `specs/005-error-handling/spec.md`。
- 所有事件监听与事件系统设计必须遵循 `specs/004-event-system/spec.md`。

## API 命名规范

- 对外 API 必须使用:
  - 读取类：getXxx 不允许使用 `fetchXxx` 或 `getXxxFromServer`
  - 添加类：addXxx / createXxx
  - 更新类：updateXxx / setXxx
  - 移除类：removeXxx（从集合移除）
  - 权限/角色：grantXxx / revokeXxx
  - 主动踢出：kickXxx（带强制语义）
  - 自己退出：leaveXxx（自愿语义）
- 内部 API 不做强制命名限制。

## 对外 API 返回格式规范

- SDK 对外方法必须返回**业务对象**，禁止把服务端 HTTP 响应包装（如 `code/data/message/path/uri/timestamp`）原样透传给调用方。
- 成功返回统一采用：
  - 有返回值：`Promise<BusinessObject>`（或数组/分页对象等业务结构）
  - 无返回值：`Promise<void>`
- 失败返回统一采用：抛出 `SDKError`（包含 SDK 错误码、原因、建议处理方式），而非返回 `{ code: non-zero }`。
- 除非功能 spec 明确要求且经评审批准，禁止在对外返回中同时出现语义重复字段（如 `result` 与 `data.result` 并存）。
- 若需要保留服务端原始响应用于排障，应通过日志/调试开关或内部接口暴露，不得污染默认对外 API 返回结构。

## 代码结构与模块拆分规范

1. **方法放置原则**
   - 对外 API 放在对外入口（ChatClient 或公开的 Manager），仅负责参数校验与编排，不承载复杂业务逻辑。
   - 领域能力放在对应领域模块（如连接/消息/会话/权限）。
   - 通用能力放在 `utils` 或独立模块。
   - 类型与常量集中在 `types` / `constants`，业务逻辑禁止硬编码字符串。
   - 配置项集中在 `config`。

2. **模块拆分原则**
   - 单一职责：一个模块只做一件清晰的事。
   - 编排与实现分离：上层只编排，下层只实现。
   - 低耦合高内聚：模块通过明确接口交互，不跨层调用。
   - 可测试性：模块可被独立 mock，便于单元测试。

3. **拆分颗粒度**
   - 一个文件聚焦一个核心概念（类或核心函数组）。
   - 函数尽量不超过 30～50 行，单文件建议不超过 200～300 行（特殊情况可例外）。
   - 复杂流程拆分为：校验 → 领域操作 → 状态更新 → 事件/日志。

4. **依赖与导出**
   - `index.ts` 仅负责聚合导出，不承载业务逻辑。
   - 外部模块只从公共入口导入，禁止直接引用内部实现文件。
   - 禁止循环依赖，必要时引入接口或抽象层解耦。

## 注释与文档规范

- 所有公共 API 必须包含完整 JSDoc。
- 复杂逻辑必须添加解释性注释。
- 所有文档与说明使用中文。

### 公共 API 双语注释与文档产出规范

- 对外 API（公开类方法、公开函数、公开类型 `interface`/`type`）必须提供**中英双语注释**，且中英文信息语义一致。
- 对外 API 方法注释必须完整包含以下块：
  - 调用方式示例（至少 1 个最小可运行示例）
  - 参数说明（逐项说明含义、取值范围、默认值、是否必填）
  - 可能错误（错误码、触发原因、推荐解决方式）
  - 返回值说明（返回类型语义、关键字段含义）
- 对外参数类型与返回类型的字段必须具备注释，确保编辑器悬浮提示可直接理解字段用途。
- 双语注释推荐统一格式标记（例如 `[zh-CN]` 与 `[en-US]`），以支持脚本按语言过滤与产出 API 文档。
- 必须提供可切换语言的文档生成脚本（如 `docs:api:zh` 与 `docs:api:en`）；对外 API 有变更时，必须同步更新对应语言文档产物。

## 测试与质量门禁

- 关键路径必须补充单元测试，覆盖正常/异常/边界场景。
- 变更必须验证正确性，默认执行 `npm run test:run && npm run lint`；若不适用必须说明理由与替代验证方式。
- 覆盖度按函数统计：对外公开 API 覆盖率必须 100%，内部方法覆盖主要逻辑，目标 80% 以上。
- 所有 REST/API 映射必须基于真实返回结构编写与验证：测试用例至少包含一条“真实接口返回样例（或等价 fixture）”。
- 若开发阶段无法确认真实返回结构，必须先向需求方索要真实请求 `curl` 与响应样例，再继续实现与测试；禁止仅依据推测字段完成 API 解析。
- 对外 API 变更必须通过“注释完整性 + 双语文档可生成性”校验（建议通过脚本或 CI gate 自动化执行）。

### 功能规格测试分层要求

- 所有新功能 `spec.md` 必须显式评估以下三层测试：
  - 单元测试（`tests/unit`）
  - 集成测试（`tests/integration`）
  - E2E 测试（`tests/e2e`）
- `spec.md` 不允许省略测试分层章节。每一层都必须填写：
  - 需要覆盖的范围
  - 计划新增或复用的测试位置
  - 若不适用，必须写清楚不适用原因
- `tasks.md` 必须把测试分层要求落成具体任务，禁止只写“补充测试”这类笼统描述。
- 对于 Web SDK：
  - 单元测试默认必需
  - 变更涉及协议编解码、连接状态机、管理器协作、缓存/同步链路时，集成测试默认必需
  - 变更影响真实 demo 主路径、登录/连接/发消息/登出等用户可见链路时，必须评估并优先补充 E2E
- 如果某层测试选择“不新增”，必须在 spec 中说明现有覆盖如何足以兜底，并在 tasks 中记录“复用现有测试/无需新增”的依据。

## 开发流程要求

- 新功能开发前需先确认是否创建功能分支。
- 大范围修改（多文件/架构调整/高风险）需先输出计划并经确认后实施。
- 变更完成后必须提交 git commit，提交信息遵循 Conventional Commits。
- 每次修改必须同步更新 CHANGELOG 与版本号。
- 使用脚手架生成 spec/tasks 时，必须保留并填写测试分层章节，不得在生成后手动删除。

## 安全与合规

- 不在日志中输出敏感信息。
- 对外输入必须进行必要校验，避免注入与非法数据传播。
- 对外文档需说明安全注意事项（如 token 管理、日志脱敏）。

## 治理

本 Constitution 优先于其他开发实践。任何例外必须明确说明理由并在变更记录中体现。修订流程如下：

1. 提出修订理由
2. 讨论并确认
3. 更新版本号与修订日期
4. 同步相关模板/文档
5. 在 CHANGELOG 中记录
